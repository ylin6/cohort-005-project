# What Knock's API offers for Cadence's wiring

Research for issue #10. These are facts only. This note makes no decisions.

- **Checked:** 2026-11-12, against docs.knock.app (the `.md` versions of each page), the npm registry, and the `knocklabs/knock-node` source on GitHub.
- **Cadence context:** React Router (framework mode, SSR), TypeScript, a SQLite/Drizzle Node server, under 100 Notifications a month on Knock's Free plan. The preferences UI is Cadence's own, and the email channel sends through Cadence's existing Postmark account.
- **Unconfirmed:** a fact marked **unconfirmed** is one the primary sources did not state outright.

## Users

| Fact | Source |
| --- | --- |
| There are three ways to identify (upsert) a user: direct `PUT /v1/users/{user_id}`, inline identification inside other server-side requests such as `POST /v1/workflows/{key}/trigger`, and bulk `POST /v1/users/bulk/identify`. | https://docs.knock.app/managing-recipients/identifying-recipients.md |
| Every identification is an upsert. Existing data is merged. | same |
| Inline identification on a trigger needs recipient **objects** (`{ "id": "user-123", ... }`). A bare ID string (`"user-123"`) refers to a user who is already identified and does not identify one. Knock guarantees that inline recipients are identified **before** the workflow runs for them. | same; https://docs.knock.app/send-notifications/triggering-workflows/api.md |
| An inline recipient can carry `channel_data`, `preferences` (deep-merged, keyed by preference-set ID such as `default`), `$trigger_data` (per-recipient data merged into `data`), and any other custom key/value pairs. | https://docs.knock.app/send-notifications/triggering-workflows/api.md |
| The docs say that sending the full recipient data on every trigger is a valid way to keep Knock's user data current without separate identify calls. | https://docs.knock.app/managing-recipients/identifying-recipients.md ("Ongoing updates") |
| Custom properties are any key/value pairs, and they can be nested. Each upsert deep-merges them. You cannot remove a property, but you can overwrite it with `null`. The total size limit is 256 kB; a direct identify over it gets a `422`. | same; https://docs.knock.app/concepts/users.md |
| A user `id` can be at most 256 characters, cannot contain `/` or `#`, and **cannot be changed** once set. Knock recommends using your primary key. | https://docs.knock.app/concepts/users.md |
| Reserved properties: `name`, `email` (needed for email steps), `avatar`, `locale`, `phone_number`, `timezone`, `created_at` (only set if you send it). | https://docs.knock.app/managing-recipients/identifying-recipients.md |
| Knock does not document a dedicated "role" or "team" field on a user. Such data would be custom properties. Knock separately has **tenants** (pass `tenant` on a trigger to scope feed items to a workspace) and **objects** (non-user entities with subscriptions). | https://docs.knock.app/concepts/users.md; https://docs.knock.app/send-notifications/triggering-workflows/api.md ("Multi-tenancy") |
| Deleting a user (`users.delete`, `DELETE /v1/users/{user_id}`) **hard-deletes** the user's properties, preferences, channel data, subscriptions, schedules, all messages sent to them (with their contents), and their activity and workflow-run logs. The deletion cannot be undone and can take up to 10 minutes to process. Bulk delete also exists. You can re-identify the same ID later, and the new user starts empty. | https://docs.knock.app/managing-recipients/deleting-users.md |
| The Users concept page describes deletion differently: "Any in-app messages that reference the user will be replaced by a 'missing user' marker". This may mean feed items where the deleted user was the *actor*. The two pages do not say this the same way, so how a deleted user appears as an actor in other users' feeds is **unconfirmed**. | https://docs.knock.app/concepts/users.md |
| Users are isolated per environment. You must identify a user separately in each environment. | https://docs.knock.app/concepts/users.md |

## Triggers

| Fact | Source |
| --- | --- |
| `POST /v1/workflows/{key}/trigger`. Body: `recipients` (required; up to 1000 per call), `actor`, `data` (JSON object, 10 MB limit), `tenant`, `cancellation_key`, `settings`. Rate-limit tier 5. | https://docs.knock.app/api-reference/workflows/trigger.md; https://docs.knock.app/send-notifications/triggering-workflows/api.md |
| The response is always `{ "workflow_run_id": "<uuid>" }`. **All workflow runs execute asynchronously.** A `200` means only that Knock accepted the trigger, not that a message was delivered. | same |
| An API trigger always runs the **last committed** version of the workflow. (The dashboard test runner uses the last *saved* version.) | https://docs.knock.app/send-notifications/testing-workflows.md |
| **`Idempotency-Key`:** a string of up to 255 characters. A retry with the same key **within 24 hours** of the original request returns the original response, with the headers `idempotent-replayed: true` and `original-x-request-id`. If the parameters differ from the original, Knock returns an error. Only **`POST /workflows/:key/trigger`** honours the header; it has no effect on other endpoints. | https://docs.knock.app/api-reference/overview/idempotent-requests.md |
| Knock caches **only `2xx` responses** for idempotency. A retry after a `4xx` or `5xx` with the same key runs the request again. | same |
| Idempotency scope: the docs speak of keys "you generate for each request" and give no other scope. Rate limits are scoped per environment (by API key). Whether one key is shared across environments or workflows is **unconfirmed**. | same; https://docs.knock.app/api-reference/overview/rate-limits.md |
| A failed API request returns JSON `{ code, message, status, type }`. Branch on `code`, not on `message`. A `429` means the request was rate-limited. | https://docs.knock.app/api-reference/overview/errors.md; https://docs.knock.app/api-reference/overview/rate-limits.md |
| **Failures after acceptance** (inside the async run): a step whose error is retryable, such as a template render error or a fetch-step error, is retried **up to 3 times in total**. If every attempt fails, the run **halts** and no later steps execute. You can retry a failed run **once**, from the dashboard debugger, within 7 days. | https://docs.knock.app/send-notifications/debugging-workflows.md ("When a workflow step fails") |
| A step is **skipped**, and the run continues, when: step conditions fail, the channel is not configured in that environment, the recipient's preferences opt out, the recipient is missing required data (for example no `email`), or a dynamic batch, delay or throttle window is invalid. | same ("When a workflow step is skipped") |
| **Provider delivery:** Knock retries a send to the provider (for example Postmark) **up to 8 times over 30 minutes** with exponential backoff, for connection errors, retryable provider errors and transient pipeline errors. The message status moves through `queued` → `delivery_attempted` → `delivered` / `bounced` / `undelivered`. You can manually retry an `undelivered` message from the dashboard. | https://docs.knock.app/send-notifications/delivering-notifications.md |
| An Inactive workflow terminates runs that reach any step. | https://docs.knock.app/concepts/workflows.md |
| **Node SDK:** `@knocklabs/node`, latest **1.41.1** (published 2026-11-10). It needs Node.js 20 LTS or later. It is a Stainless-generated TypeScript client: `new Knock({ apiKey })` (default `process.env.KNOCK_API_KEY`), then `client.workflows.trigger(key, { recipients, data, ... })`. | https://registry.npmjs.org/@knocklabs/node; https://github.com/knocklabs/knock-node/blob/main/README.md |
| The SDK throws subclasses of `APIError` on non-2xx: `BadRequestError` (400), `AuthenticationError` (401), `PermissionDeniedError` (403), `NotFoundError` (404), `UnprocessableEntityError` (422), `RateLimitError` (429), `InternalServerError` (5xx), `APIConnectionError`, and `APIConnectionTimeoutError` (default timeout 1 minute). | https://github.com/knocklabs/knock-node/blob/main/README.md |
| The SDK **retries automatically 2 times by default**, on connection errors, 408, 409, 429 and 5xx. The `maxRetries` option changes this. | same ("Retries") |
| The SDK sends an `Idempotency-Key` header on **every non-GET request**. When you don't pass one, it auto-generates `stainless-node-retry-<uuid>` and reuses it across its own retries. Pass your own with the per-request option `{ idempotencyKey }`. | https://github.com/knocklabs/knock-node/blob/main/src/client.ts (`idempotencyHeader = 'Idempotency-Key'`, `defaultIdempotencyKey()`); https://github.com/knocklabs/knock-node/blob/main/src/internal/request-options.ts |
| The SDK also provides `signUserToken` (from `@knocklabs/node/lib/tokenSigner`) to sign the RS256 user JWT that the client-side feed needs when **enhanced security mode** is on. Enhanced security is off by default and recommended for production. | https://docs.knock.app/in-app-ui/security-and-authentication.md |

## Batching

| Fact | Source |
| --- | --- |
| A batch is a **workflow function step**. The first trigger for a recipient that reaches it opens a batch. Later triggers for the same recipient while the batch is open are added as `activities`, **and their own workflow runs terminate at the batch step**. When the window closes, the run that opened the batch continues to the next steps. | https://docs.knock.app/designing-workflows/batch-function.md |
| Batches are always per **recipient**. The optional **batch key** groups them further. It resolves to a `data` path (`page_id` → `data.page_id`) or to Liquid over `data`, `recipient`, `actor` and `tenant` (for example `{{data.eventType}}-{{actor.id}}`). | same ("Selecting a batch key") |
| The window opens at the **first** trigger. It can be **fixed** (seconds, minutes, hours or days), **dynamic** (from a variable: an ISO-8601 timestamp, a duration, or a window rule such as "daily at 9:30" in the recipient's timezone), **relative**, or **sliding** (each trigger extends it, up to a required maximum). The maximum is 90 days. An open window is immutable unless it is sliding. | same ("Setting the batch window") |
| An optional **maximum activity limit** (2–1000) closes the batch early. Optional **"immediately flush leading item"** sends the first item at once and batches the rest. | same |
| You cannot close a batch from a trigger; the documented workaround is a sliding window with a tiny maximum. A cancellation (`cancellation_key`) removes one item from an open batch. A batch that is empty at close sends nothing. | same (FAQ; "Using workflow cancellation with batches") |
| **Per-channel differences:** the docs describe the batch step as affecting *the steps after it* in the workflow. A run that joins a batch terminates *at* the batch step. **Unconfirmed:** whether channel steps placed before the batch step run once per trigger. No page states this outright, and the docs show no option to batch one channel differently from another within one batch step. | same ("How batching works"); https://docs.knock.app/send-notifications/debugging-workflows.md ("Debugging workflows with a batch step") |
| **What templates see** after the batch closes: `total_activities`, `total_actors`, `activities` (up to **10**, first-10 or last-10 by "batch order", always in chronological order; each holds that trigger's `data` and the actor/recipient), and `actors` (up to 10 unique actors). Going beyond 10 (up to 100) is **Enterprise-only**. | https://docs.knock.app/designing-workflows/batch-function.md ("Working with batches in your templates"); https://docs.knock.app/manage-your-account/knock-plans.md |
| After a batch, the top-level `data` is a **flattened merge**: nested objects and arrays are removed, strings are truncated to 256 characters, and the latest trigger wins on key collisions. The docs recommend reading per-trigger data from `activities`. | same ("The `data` payload") |
| **Feed item** shape (`GET /v1/users/{id}/feeds/{channel_id}`, `mode=rich`, the default): each entry carries `activities`, `actors`, `total_activities`, `total_actors`, `data`, `blocks` (rendered content), `source.key` (workflow key), `tenant`, `inserted_at` and `updated_at`. Read, seen and archived state can be filtered on (`status`, `archived`); which per-item status fields the response carries is **unconfirmed**, because the reference example shows none. `mode=compact` drops `activities` and `total_activities`. | https://docs.knock.app/api-reference/users/feeds/list_items.md |
| Only the attachments of the activity that opened the batch go out with a batched email. | https://docs.knock.app/designing-workflows/batch-function.md (FAQ) |
| Order within a batch is not guaranteed for requests less than 2 s apart. | same (FAQ) |
| New batch steps (since 2026-08-20) default to "latest" version mode: an open batch survives a new workflow commit and continues on the latest version. | same ("Setting the workflow version mode") |

## Feed history

| Fact | Source |
| --- | --- |
| **In-app feed notifications are available indefinitely.** The Feeds API and message status updates are **not** subject to the retention policy. | https://docs.knock.app/manage-your-account/data-retention.md; https://docs.knock.app/concepts/messages.md |
| Other data falls under the plan retention policy: **30 days** on all non-Enterprise plans (90 days on Enterprise). This covers message logs (contents, events, delivery logs), workflow run logs, and outbound webhook and source logs. API logs are kept 30 days on every plan. Custom retention is not supported. | https://docs.knock.app/manage-your-account/data-retention.md |
| The pricing page lists the Free plan's feed retention as "Unlimited", with the note "No limit, but can be configured", and its logs as "30-day retention". | https://knock.app/pricing |
| Paging a user's full feed: `GET /v1/users/{user_id}/feeds/{channel_id}` returns entries newest first, with **cursor pagination** (`after`, `before`, `page_size`, default 50). It accepts filters `status`, `archived` (for example `only` to list archived items, which the stock component hides), `source` (workflow key), `tenant`, `workflow_categories`, `trigger_data`, and `inserted_at.{gt,gte,lt,lte}`. The response `meta` has `total_count`, `unread_count` and `unseen_count`. The feed endpoint's rate limit is always scoped per user and per environment. | https://docs.knock.app/api-reference/users/feeds/list_items.md; https://docs.knock.app/integrations/in-app/feeds.md |
| The Node SDK supports auto-pagination (`for await` over list methods). | https://github.com/knocklabs/knock-node/blob/main/README.md ("Auto-pagination") |
| Once generated, a feed message's content is immutable; only its status (read, archived and so on) can change. To correct one, archive it and trigger again. | https://docs.knock.app/integrations/in-app/feeds.md |
| Deleting a user hard-deletes all messages sent to that user. | https://docs.knock.app/managing-recipients/deleting-users.md |

## Preferences

| Fact | Source |
| --- | --- |
| A `PreferenceSet` has the keys `categories`, `channels` (by channel UUID), `channel_types` (`email`, `in_app_feed`, ...), and `workflows` (by workflow key). Each takes a boolean, or a nested `{ channel_types, channels }` (with optional `conditions`). The `default` set also has `commercial_subscribed`. Per-workflow per-channel looks like `{"workflows": {"invoice-issued": {"channel_types": {"email": true}}}}`. | https://docs.knock.app/preferences/overview.md |
| **Read:** `GET /v1/users/{user_id}/preferences/{id}` (`id` usually `default`; optional `tenant`). List all sets: `GET /v1/users/{user_id}/preferences`. | https://docs.knock.app/api-reference/users/get_preferences.md; https://docs.knock.app/api-reference/users/list_preferences.md |
| **Write:** `PUT /v1/users/{user_id}/preferences/{id}` **replaces** the whole set by default. Send `"__persistence_strategy__": "merge"` to deep-merge instead. Node: `client.users.setPreferences(userId, 'default', {...})`. Bulk set (up to 1000 users) is an async job that overwrites. | https://docs.knock.app/api-reference/users/set_preferences.md; https://docs.knock.app/preferences/overview.md |
| Preferences can also be deep-merged inline on identify or trigger (the `preferences` key on a recipient). The docs advise using the preferences endpoints unless you want that merge. | https://docs.knock.app/managing-recipients/identifying-recipients.md (FAQ) |
| **Evaluation:** anything unset defaults to `true`, and a message sends only if **every** applicable preference evaluates to `true`. A `false` category blocks the message even if the channel is `true`. A `channels` entry overrides a `channel_types` entry. The merge order is recipient set over environment default; with a tenant, it is recipient tenant set over tenant default over environment default. | https://docs.knock.app/preferences/overview.md |
| **Bypassing preferences (locked channel):** a workflow-level setting. "Manage workflow" → enable **"Override recipient preferences"**, then commit. When enabled, "the workflow will send to all of its channels, regardless of the recipient's preferences." | https://docs.knock.app/preferences/overview.md ("Advanced concepts" → Workflow overrides) |
| The override is stored as `settings.override_preferences: true` on the workflow (Management API Workflow schema). Templates can read it as the Liquid variable `workflow.override_preferences`, described as "Whether the workflow is configured to ignore recipient preferences and send to all channels". | https://docs.knock.app/mapi-reference/workflows/schemas/workflow.md; https://docs.knock.app/template-editor/variables.md |
| **Unconfirmed / not found:** a per-**step** override, meaning one channel step that ignores preferences while others in the same workflow honour them. The WorkflowStep schema has no preference field. The channel-step page lists the preference check as a fixed part of step execution. | https://docs.knock.app/mapi-reference/workflows/schemas/workflow_step.md; https://docs.knock.app/designing-workflows/channel-step.md |
| Per-tenant preferences are **Enterprise-only**. | https://docs.knock.app/manage-your-account/knock-plans.md |
| A Knock-hosted preference page and React `usePreferences` hooks exist. Both are optional; a custom preference center can use the REST API directly. | https://docs.knock.app/preferences/overview.md ("Going live with preferences"); https://docs.knock.app/preferences/custom-preference-center.md |

## Dev and tests

| Fact | Source |
| --- | --- |
| A new account has **only a production environment**. "Enable environments" adds **Development**, which becomes the CLI and Management API default and starts empty (it copies only the default email layout). This cannot be turned off. You can add staging or other environments and branches after that. | https://docs.knock.app/version-control/environments.md; https://docs.knock.app/version-control/overview.md |
| Each environment has its own API keys and isolated data (users, tenants, objects, messages, logs). Workflows and layouts are version-controlled content that you **commit** and then **promote** upward. Content can only be edited in the environment where it was created. | https://docs.knock.app/version-control/environments.md |
| The Free plan has unlimited environments and up to 10,000 messages a month with no hard cap. A message counts per user, per channel, per successful delivery. **Sandboxed messages don't count toward usage.** | https://knock.app/pricing; https://docs.knock.app/manage-your-account/knock-plans.md |
| **Sandbox mode** is a per-channel, per-environment setting (Advanced). Knock renders and previews the message but never calls the provider. It works on all channel types **except in-app**. You can save a Postmark config in sandbox mode without a Postmark API key. When sandbox is on, channel conditions are not evaluated. The Postmark channel lists "Sandbox mode" among its features. | https://docs.knock.app/integrations/overview.md ("Sandbox mode"); https://docs.knock.app/integrations/email/postmark.md |
| A per-trigger override exists: `settings: { sandbox_mode: true, skip_delay: true }` forces every message in that run into sandbox (whatever each channel's config says) and skips delay steps. Whether `skip_delay` also skips **batch** windows is **unconfirmed**; the docs name only delay steps. | https://docs.knock.app/send-notifications/triggering-workflows/api.md ("Testing workflows with trigger settings") |
| **Channel conditions** (per environment) can restrict a channel, for example to recipients on your own domain in non-prod. Postmark config also allows a per-environment **To override**, a From name such as "(dev)", and a payload override. | https://docs.knock.app/integrations/overview.md; https://docs.knock.app/integrations/email/postmark.md |
| A built-in **Knock test email channel** exists: 100 emails a month, only to Knock account members' addresses (anyone else gets the error `knock_recipient_not_allowed`). | https://docs.knock.app/integrations/email/knock-test.md |
| Postmark integration: Knock sends `Metadata.knock_message_id`, `Metadata.knock_recipient_id`, and `Tag` = workflow key. An optional Postmark webhook can feed `delivered` and `bounced` statuses back to Knock. | https://docs.knock.app/integrations/email/postmark.md |
| Dashboard test runner and `knock workflow run` CLI let you run a whole workflow or a single step. | https://docs.knock.app/send-notifications/testing-workflows.md |
| **Stubbing Knock in tests:** I found **no documented** mock, fake server or test helper for Knock. A search of `llms-full.txt` for mock, stub, jest, vitest and msw found nothing relevant. **Unconfirmed / not offered.** The Node SDK does provide seams: `baseURL` (or the env var `KNOCK_BASE_URL`) to point at a local fake, a custom `fetch` option, and `maxRetries: 0`. | https://docs.knock.app/llms-full.txt; https://github.com/knocklabs/knock-node/blob/main/README.md ("Customizing the fetch client"); https://github.com/knocklabs/knock-node/blob/main/src/client.ts |
| `@knocklabs/react` latest is **0.15.1** (2026-11-06). Peer dependencies: `react` and `react-dom` 17–19. `next` and `@tanstack/react-router` are optional peers. It is built on `@knocklabs/client` 0.23.1. | https://registry.npmjs.org/@knocklabs/react; https://registry.npmjs.org/@knocklabs/client |
